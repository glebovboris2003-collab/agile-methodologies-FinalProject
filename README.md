# Этап 1. Выбор и адаптация методологии

## 1.1. Выбор методологии

Для разработки LLM-ассистента FinCore я выбираю **Kanban**.

Основная причина - высокая неопределённость проекта. Команда создаёт для компании новый продукт, требования к которому ещё не сформированы окончательно. Часть требований может измениться после первых демонстраций, а в процессе разработки могут появляться новые задачи, связанные с качеством ответов LLM, безопасностью данных и интеграцией с существующей системой.

Kanban позволяет не фиксировать большой набор задач на несколько недель вперёд, а постоянно выбирать следующую наиболее приоритетную работу из backlog. Для FinCore это удобно, потому что продуктовый директор может изменить приоритет после получения обратной связи от клиентов.

Кроме того, команда небольшая и неоднородная. ML-инженер занят проектом примерно на 80%, frontend-разработчик доступен только на 50%, backend-разработчик ещё не имеет опыта с LLM, а data analyst не занимается production-разработкой. Поэтому скорость выполнения задач разными участниками будет отличаться.

В Scrum команда обычно формирует Sprint Backlog и старается сохранить его относительно стабильным до конца спринта. Это создаёт хороший ритм работы, особенно когда необходимо регулярно демонстрировать завершённый результат. У FinCore также есть фиксированные контрольные сроки: демо через 6 недель и публичный релиз через 3 месяца.

Однако я считаю, что в данном случае преимущества Kanban важнее. Команда впервые разрабатывает LLM-функциональность, поэтому заранее точно оценить сложность многих задач трудно. Например, эксперимент с качеством LLM может закончиться как за один день, так и потребовать нескольких дополнительных итераций.

При этом я не отказываюсь от временных контрольных точек. Каждые две недели команда проводит review результата и планирует цели следующего периода. Таким образом, Kanban обеспечивает гибкость потока задач, а регулярные review позволяют контролировать движение к демонстрации через 6 недель.

## 1.2. Адаптация Kanban

Для проекта будет использоваться общая Kanban-доска со следующими колонками:

**Backlog → Ready → In Progress → Code Review / Testing → Done**

### Backlog

Здесь находятся все требования и технические задачи проекта.

### Ready

В эту колонку попадают задачи, которые достаточно подробно описаны и могут быть взяты разработчиком без дополнительного уточнения.

Для перехода задачи в Ready необходимо определить:

- цель;
- исполнителя;
- критерии приёмки;
- основные зависимости;
- требования безопасности, если работа связана с пользовательскими данными.

### In Progress

Задачи, которые прямо сейчас выполняются командой.

Для этой колонки вводится **WIP limit = 4**.

Это означает, что команда не может одновременно выполнять более четырёх основных задач.

Такое ограничение необходимо, чтобы сотрудники не начинали большое количество работ одновременно и чаще доводили начатое до результата.

### Code Review / Testing

Здесь находятся задачи, разработка которых завершена, но результат ещё необходимо проверить.

Поскольку отдельного QA-инженера в команде нет, тестирование распределяется между участниками.

### Done

Задача считается завершённой только после выполнения критериев приёмки и необходимых тестов.

Дополнительно каждые две недели проводится:

- review готового функционала;
- анализ выполненных задач;
- обновление приоритетов backlog;
- короткая ретроспектива.

Таким образом, команда не работает спринтами в классическом понимании Scrum, но имеет регулярные точки контроля.

## 1.3. Организация распределённой работы

Команда находится в Москве, Екатеринбурге и Алматы, поэтому обязательные ежедневные видеозвонки могут создавать лишние сложности.

Основная коммуникация будет асинхронной.

Каждый рабочий день участник оставляет короткое сообщение:

- что завершено;
- что находится в работе;
- какие существуют блокирующие проблемы.

Для сложных вопросов проводится отдельный короткий созвон с необходимыми участниками, а не со всей командой.

Алина работает только 50% времени, поэтому её frontend-задачи заранее переводятся в Ready и не меняются без веской причины.

Иван в начале проекта работает совместно с ML-инженером над интеграцией с LLM. По мере получения опыта он сможет брать такие задачи самостоятельно.

Данияр используется как основной эксперт по данным. Он определяет необходимые источники данных, проверяет SQL-запросы, помогает создавать эталонные ответы и описывает бизнес-правила.

ML-инженер выполняет функции tech lead: отвечает за архитектуру LLM-части, качество ответов и техническую координацию проекта.

# Этап 2. Backlog: user stories и приоритизация

## 2.1. Приоритизация требований

### Must have

**R-01 — вопросы по данным аккаунта**

Это основная функция продукта. Если пользователь не может задать вопрос и получить ответ по своим данным, LLM-ассистент не выполняет своё назначение.

**R-02 — объяснение строк отчёта**

Это один из основных бизнес-сценариев, ради которого создаётся ассистент.

**R-07 — журналирование запросов**

Для финансовой системы важно иметь возможность расследовать ошибочные или спорные ответы.

**R-11 — анонимизация ФИО и ИНН**

Требование напрямую связано с ограничениями безопасности. Финансовые данные нельзя передавать во внешнюю LLM в исходном виде.

### Should have

**R-03 — вопросы о налоговом законодательстве**

Функция полезна, однако для неё необходимо создать отдельный механизм получения актуальной нормативной информации.

**R-04 — история диалогов**

Повышает удобство использования, но пользователь может работать с первой версией ассистента и без сохранения истории.

**R-05 — ссылки на статьи НК РФ**

Функция повышает доверие к ответам, но требует надёжного источника актуальных документов.

**R-08 — обнаружение возможных ошибок**

Полезная возможность, но фактически представляет отдельный аналитический функционал.

**R-10 — ответ за 5 секунд**

Скорость важна для пользовательского опыта, однако сначала необходимо обеспечить безопасность и корректность ответа.

**R-14 — внутренний dashboard**

Необходим команде для анализа продукта после появления реального пользовательского трафика.

**R-15 — оценка ответа**

Поможет собирать обратную связь после запуска.

### Can wait

**R-06 — заполнение форм с помощью голосового ввода**

Одновременно требует распознавания речи, генерации документов и дополнительного интерфейса.

**R-09 — мобильные приложения**

Для MVP можно использовать существующий web-интерфейс.

**R-12 — казахский язык**

Можно реализовать после проверки русскоязычной версии продукта.

**R-13 — действия от имени пользователя**

Создание платёжных поручений значительно увеличивает риски. Для такой функции потребуется отдельная система авторизации и подтверждения действий.

## 2.2. User stories

### US-01 — R-01. Вопрос по данным аккаунта

**Как клиент FinCore, я хочу задать ассистенту вопрос о данных моей компании, чтобы получить ответ без обращения в службу поддержки.**

Критерии приёмки:

1. Пользователь может отправить текстовый вопрос на русском языке.
2. Система использует данные только текущего аккаунта.
3. Если данных для ответа недостаточно, ассистент сообщает об этом пользователю.

---

### US-02 — R-02. Объяснение показателя

**Как бухгалтер, я хочу получить объяснение изменения показателя в отчёте, чтобы понимать причину изменения расчёта.**

Критерии приёмки:

1. Ассистент получает необходимые агрегированные данные.
2. В ответе объясняется причина изменения показателя.
3. Результат проверяется на заранее подготовленных тестовых примерах.

---

### US-03 — R-11. Защита данных

**Как клиент FinCore, я хочу, чтобы мои персональные данные не передавались внешней LLM, чтобы конфиденциальная информация оставалась защищённой.**

Критерии приёмки:

1. ФИО заменяются внутренними идентификаторами.
2. ИНН не передаётся внешней модели.
3. Если данные невозможно безопасно подготовить, запрос к внешнему API не выполняется.

---

### US-04 — R-07. Аудит

**Как сотрудник FinCore, отвечающий за аудит, я хочу иметь журнал взаимодействий с ассистентом, чтобы расследовать неправильные ответы и технические ошибки.**

Критерии приёмки:

1. Для каждого обращения сохраняется время и идентификатор запроса.
2. Сохраняется результат выполнения.
3. Журнал не содержит открытых персональных данных.

---

### US-05 — R-10. Производительность

**Как пользователь, я хочу быстро получать ответы ассистента, чтобы его использование не замедляло мою работу.**

Критерии приёмки:

1. Для каждого запроса измеряется время обработки.
2. Для типовых запросов рассчитывается 95-й перцентиль времени ответа.
3. Система корректно сообщает пользователю о превышении тайм-аута.

---

### US-06 — R-04. История

**Как пользователь, я хочу иметь доступ к предыдущим диалогам, чтобы возвращаться к ранее полученной информации.**

Критерии приёмки:

1. История сохраняется после завершения сессии.
2. Пользователь имеет доступ только к истории своей организации.
3. Вопросы и ответы отображаются в исходном порядке.

---

### US-07 — R-15. Обратная связь

**Как пользователь, я хочу оценить ответ ассистента, чтобы сообщить команде FinCore о качестве результата.**

Критерии приёмки:

1. Пользователь может поставить положительную или отрицательную оценку.
2. Оценка связывается с конкретным ответом.
3. Информация доступна команде для последующего анализа.

# Этап 3. Планирование первой итерации и AI-ассистирование

## 3.1. Первый период работы

Несмотря на использование Kanban, для контроля проекта выделяется первый **двухнедельный период**.

Главная цель периода:

**получить минимальный безопасный end-to-end сценарий, в котором пользователь задаёт вопрос о показателе, FinCore получает необходимые данные и возвращает ответ через LLM.**

### План работ

| Задача | Ответственный | Оценка | Причина включения |
|---|---|---:|---|
| Определить архитектуру передачи данных | ML-инженер + Иван | 2 дня | Необходимо определить границы между FinCore и LLM |
| Выбрать один тестовый бизнес-сценарий | Данияр + ML-инженер | 1 день | Нужен ограниченный сценарий для первой проверки |
| Подготовить SQL для получения данных | Данияр | 2 дня | LLM не имеет прямого доступа к БД |
| Реализовать слой получения данных | Иван | 2 дня | Необходим backend для связи с существующей системой |
| Сделать прототип анонимизации | Иван + ML-инженер | 2 дня | Критическое условие безопасности |
| Подключить LLM API | ML-инженер | 2 дня | Проверка основного технического решения |
| Создать минимальный API чата | Иван | 2 дня | Связывает интерфейс и LLM |
| Создать простой интерфейс чата | Алина | 3 дня | Позволяет продемонстрировать пользовательский сценарий |
| Добавить журналирование | Иван | 1 день | Нужно для анализа запросов |
| Подготовить 20 тестовых вопросов | Данияр | 2 дня | Проверка качества ответов |
| Выполнить end-to-end тестирование | Вся команда | 1 день | Проверка результата периода |

Работы выполняются не строго последовательно. Например, пока Данияр готовит данные, Алина может начать создавать интерфейс по заранее согласованному контракту API.

WIP limit не позволяет команде одновременно иметь больше четырёх крупных задач в статусе In Progress.

## 3.2. Definition of Done

Задача считается завершённой, если:

- выполнены критерии приёмки;
- код прошёл review;
- автоматические тесты выполняются успешно;
- функциональность развёрнута в тестовом окружении, если это применимо;
- отсутствует передача запрещённых персональных данных;
- основные ошибки корректно обрабатываются;
- документация обновлена;
- результат можно продемонстрировать команде.

## 3.3. Промт №1 — анализ архитектурных рисков

Мы разрабатываем LLM-ассистента для финтех SaaS-системы FinCore. Backend работает на Python/FastAPI, данные клиентов находятся в PostgreSQL, а внешней LLM запрещено предоставлять прямой доступ к базе данных. Финансовые данные нельзя передавать внешней модели в сыром виде, а ФИО и ИНН необходимо анонимизировать. На первом этапе пользователь должен задать вопрос о показателях своего аккаунта и получить объяснение от LLM. Команда состоит из ML-инженера, backend-разработчика, frontend-разработчика и data analyst. Проанализируй архитектуру такого решения и перечисли основные точки возможной утечки данных. Для каждого риска предложи техническую меру защиты и способ проверки. Отдельно перечисли риски, которые необходимо проверить до первой демонстрации.

---

## 3.4. Промт №2 — декомпозиция функциональности

Мы планируем реализовать первый end-to-end сценарий LLM-ассистента FinCore: пользователь спрашивает, почему изменился показатель в его отчёте, система получает необходимые данные из PostgreSQL через backend и передаёт во внешнюю LLM только разрешённые агрегированные или анонимизированные данные. Прямой доступ модели к базе запрещён. Команда состоит из одного ML-инженера, одного backend-разработчика, frontend-разработчика с загрузкой 50% и data analyst, который хорошо знает SQL, но не пишет production backend. Разбей эту функциональность на технические задачи размером примерно 1–2 рабочих дня. Для каждой задачи укажи результат, зависимости и специалиста, который лучше всего подходит для выполнения. Укажи задачи, которые могут выполняться параллельно. В конце выдели минимальный набор работ, достаточный для первой демонстрации.

---

## 3.5. Где AI полезен, а где нет

AI-ассистирование может значительно ускорить проектирование и планирование проекта. Например, LLM удобно использовать для первоначальной декомпозиции задач, создания вариантов критериев приёмки, поиска возможных edge cases и составления тестовых сценариев.

AI также может помочь Ивану быстрее освоить особенности интеграции LLM API и объяснить незнакомые подходы, связанные с RAG, prompt engineering и обработкой ответов модели.

При этом результаты AI нельзя автоматически считать правильными. Модель не имеет полного знания внутренней архитектуры FinCore, реальной структуры базы данных и загрузки сотрудников.

Особенно ограниченно AI должен использоваться для решений, связанных с безопасностью и законодательством. Финальные правила анонимизации должны определяться разработчиками и требованиями безопасности компании.

Ответы о налоговом законодательстве также нельзя принимать без проверки по актуальным источникам.

Кроме того, реальные данные клиентов нельзя копировать во внешние LLM для анализа или тестирования.

Поэтому AI в проекте является инструментом для ускорения анализа и подготовки вариантов решения, но не заменяет ответственность специалистов и Product Owner.

# Этап 4. Работа с изменением требований

## 4.1. Анализ R-16

На третьей неделе появляется новое требование:

**R-16 — ассистент должен отвечать на вопросы о текущем статусе персонала: кто вышел на работу, кто находится в отпуске и кто уволился.**

Это требование обладает высокой бизнес-ценностью, потому что крупнейший клиент готов связать с ним продление контракта на два года.

### Техническая сложность

Архитектуру LLM существенно менять не требуется.

Уже существует общий поток:

**пользователь → FinCore backend → безопасные данные → LLM → ответ.**

Необходимо подключить ещё один тип данных — кадровые.

Данияр должен определить:

- таблицы с кадровой информацией;
- правила определения статуса;
- временную актуальность данных;
- тестовые примеры.

Иван реализует backend-функцию получения кадровых данных.

ML-инженер добавит распознавание соответствующего типа вопросов и правила формирования контекста.

Также необходимо проверить права доступа. Пользователь одной организации не должен иметь возможность получить информацию о сотрудниках другой организации.

### Пример минимальных вопросов для демо

- Кто сегодня работает?
- Кто сейчас находится в отпуске?
- Работает ли конкретный сотрудник?
- Кто был уволен?

---

## 4.2. Влияние на текущий план

При использовании Kanban добавить новое требование проще, чем при фиксированном Sprint Backlog.

Однако это не означает, что R-16 можно просто добавить поверх всей существующей работы.

После завершения уже начатых критических задач R-16 перемещается в верхнюю часть колонки Ready.

Для него временно вводится высокий класс обслуживания — **Expedite**.

При этом WIP limit сохраняется.

Это означает:

- уже почти завершённые задачи доводятся до Done;
- новые задачи низкого приоритета не начинаются;
- R-16 получает освободившуюся мощность команды.

Переносятся:

- R-04 — история диалогов;
- R-14 — dashboard;
- R-15 — пользовательские оценки.

Не переносятся:

- R-11 — безопасность данных;
- R-07 — аудит;
- базовая функциональность R-01.

---

## 4.3. Решение

Я принимаю решение **взять R-16 в работу сразу**.

Основная причина — конкретная коммерческая ценность требования. От него зависит продление крупного контракта, а данные уже существуют внутри FinCore.

Кроме того, новая функция использует уже создаваемую архитектуру и не требует полностью отдельной системы.

Однако необходимо ограничить scope.

К демонстрации реализуется только чтение кадровых статусов.

Ассистент не будет:

- изменять кадровые данные;
- оформлять отпуск;
- увольнять сотрудников;
- редактировать смены;
- проводить полноценную HR-аналитику.

Такой подход позволяет удовлетворить основную потребность клиента без значительного расширения проекта.

---

## 4.4. Сообщение продуктовому директору

Мы можем добавить работу с кадровыми статусами к ближайшей демонстрации, потому что основная архитектура ассистента уже позволяет подключать дополнительные источники данных. Предлагаю ограничить первую версию вопросами о том, кто работает, находится в отпуске или уволен. При этом необходимо проверить права доступа и не допустить передачи персональных данных во внешнюю модель. Чтобы сохранить срок демонстрации, история диалогов, dashboard и система оценок ответов временно получат более низкий приоритет. Уже начатые критические задачи по безопасности мы завершим, после чего R-16 станет следующей основной работой команды. Таким образом, мы сможем показать клиенту нужный сценарий без существенного изменения архитектуры и без отказа от требований безопасности.
